# 결과보고서 작성 규약

- **적용 대상**: `plan_d_submission/report/결과보고서.md`와 그 PDF. 발표자료에도 같은 규약을 쓴다.
- **근거**: 비즈니스 문서 작성 8원칙(김재성, 맥킨지 출신 강연)을 이 보고서와 공식 양식(본문 휴먼명조 14pt, 줄간격 160%)에 맞게 구체화했다.
- **강제 방법**: 기계로 확인할 수 있는 항목은 `report/check_style.py`가 검사한다. 나머지는 제출 전 검토 체크리스트(§3)로 확인한다.
- **수치 검사와의 관계**: 수치 정확성은 `report/check_numbers.py`가 따로 검사한다. 두 검사를 모두 통과해야 제출한다.

## 1. 8개 규약

### 규약 1. 보고서만 읽어도 이해되어야 한다

**원칙.** 말로 설명해야 이해되는 문서는 잘못 쓴 문서다. 말로 설명할 내용은 문서 안에 압축해서 들어 있어야 한다.

**이 보고서에서의 규칙**

- 심사위원은 보고서 PDF만 읽는다. 발표 전에 서면평가로 상위 8팀이 정해지므로 **보고서가 유일한 설명 수단**이다.
- 용어는 처음 나올 때 한 줄로 정의한다. 예: 버스트, window, conformal p-value, 평가 블록, 1단·2단, 빨강·노랑.
- 표·그림의 제목만 읽어도 **대상·단위·표본 수**를 알 수 있어야 한다.
  - 나쁜 예: "표 2-9. 분해"
  - 좋은 예: "표 2-9. 판정 규칙별 오경보 window 수 (평가 블록 정상 2,929 + 고장 428)"
- 작업 과정의 내부 용어는 본문에 쓰지 않는다. 금지: "검토자", "감사", "클라우드", "노트북", "Plan A~H", "DL-0xx", "사전판정". 결정 기록은 부록 A에서만 DL 번호로 인용한다.
- 파일 이름(`*.csv`)은 표 아래 출처 줄에만 쓴다. 본문 문장에는 쓰지 않는다.

**확인 방법**: 독립 검토자에게 PDF만 주고 각 장의 주장을 다시 설명하게 한다. 그 설명이 문서와 다르면 해당 절을 고친다. (§3 체크리스트)

### 규약 2. 절마다 주장 하나 (또는 요약 하나)

**원칙.** 한 페이지에는 주장 하나 또는 요약 하나가 있어야 한다. 대부분은 주장이어야 한다.

**이 보고서에서의 규칙**

- 보고서는 페이지 단위 슬라이드가 아니므로 **절(###) 하나가 한 페이지에 해당**한다.
- 각 절은 주장 하나를 위해 존재한다. 주장이 두 개면 절을 나눈다.
- 장(□ 제n장) 첫머리에는 그 장 전체를 요약하는 문장을 둔다.
- 내용요약(표지)은 보고서 전체의 요약이다.

### 규약 3. 주장과 근거는 동치여야 한다 (매핑)

**원칙.** 주장만 있고 근거가 없으면 잘못된 문서다. 근거만 있고 주장이 없어도 잘못된 문서다. 주장에 담긴 요소는 아래 근거로 모두 뒷받침되어야 하고, 아래 근거는 모두 주장 안에 포함되어야 한다.

**이 보고서에서의 규칙**

- 헤드 메시지에 나온 수치·주장 요소마다 같은 절 안에 그것을 보여주는 **표·그림·수치가 하나 이상** 있어야 한다.
- 절 안의 모든 표·그림은 헤드 메시지의 어떤 요소를 뒷받침해야 한다. 어느 요소에도 연결되지 않는 표는 삭제하거나 부록으로 보낸다.
- 근거가 없는 주장은 쓰지 않는다. 근거를 만들거나 주장을 지운다.

**확인 방법**: 절마다 "헤드 요소 ↔ 근거" 대응표를 검토 체크리스트에서 채운다(§3).

### 규약 4. 형용사·부사·지시대명사를 쓰지 않는다. 숫자와 명사로 쓴다

**원칙.** "엄청난 성장", "심각한 문제"는 읽는 사람마다 다르게 해석된다. "50% 성장", "일 사용자 수 12% 감소"는 누가 읽어도 같다. "이것·그것"은 가리키는 대상을 명사로 적는다.

**이 보고서에서의 규칙**

- **정도 표현 금지**: 매우, 크게, 상당히, 뚜렷이, 심각한, 엄청난, 탁월한, 현저히, 훨씬, 아주, 대폭, 막대한, 강력한, 충분히, 다소, 약간, 거의, 굉장히, 우수한.
  → 숫자와 비교 기준으로 바꾼다.
  - 나쁜 예: "오경보가 크게 줄었다"
  - 좋은 예: "오경보 window가 241개에서 3개로 줄었다(평가 블록)"
- **지시어 금지**: 이것, 그것, 저것, 이는, 이를, 이에, 이로, 이러한, 그러한, 해당, 상기, 위의, 아래의. 관형사 "이 ○○", "그 ○○"도 쓰지 않는다.
  → 가리키는 명사를 적는다.
  - 나쁜 예: "이 구조는 설계를 바꾼다"
  - 좋은 예: "599개 버스트 구조는 window 설계를 바꾼다"
- 비교에는 반드시 기준을 쓴다.
  - 나쁜 예: "높은 오경보율"
  - 좋은 예: "오경보율 8.23%(교차검증 0.27%의 30배)"

**확인 방법**: `check_style.py`가 금지어를 0건으로 강제한다(표·출처 줄 포함).

### 규약 5. 가독성 — 출처·주석 외에는 12pt 미만 금지

**원칙.** 한 쪽에 우겨 넣으려고 글자를 줄이지 않는다. 12pt 미만은 출처와 주석에만 허용한다.

**이 보고서에서의 규칙** (공식 양식과 결합)

| 요소 | 크기 |
|---|---|
| 본문 | 14pt (양식 "휴먼명조 14, 줄간격 160") |
| 제목 | 장 16pt, 절 14pt 굵게 |
| **표 본문, 표·그림 제목, 목록, 헤드 메시지** | **12pt 이상** |
| 출처 줄(`근거:`), 각주, 쪽번호 | 10pt (양식 "* 휴먼명조 10") |
| 그림 안 글자 | 인쇄 크기 기준 12pt 이상 |

- 표의 열은 최대 7개다. 넘으면 표를 나누거나 부록으로 보낸다.
- 한 문장은 2줄(약 80자) 이내를 권장한다.
- 분량이 넘치면 글자를 줄이지 않고 내용을 부록으로 옮긴다.

**확인 방법**: `check_style.py`가 `build_report_pdf.py`의 CSS 글자 크기를 검사한다.

### 규약 6. 모든 절에 헤드 메시지

**원칙.** 헤드 메시지는 그 페이지 전체를 포괄하는 주장이나 요약을 2줄 이내의 한 문장으로 쓴 것이다. 헤드 메시지만 읽어도 문서 전체가 이해되어야 한다. 헤드 메시지를 이어 읽는 것이 곧 문서의 스토리라인이다.

**이 보고서에서의 규칙**

- 모든 절(###)과 장(## □) 제목 바로 다음 줄에 헤드 메시지를 둔다.
- 헤드 메시지는 **굵은 한 문장, 80자 이내, 숫자 포함**이다.
- 예: `**동결 구성의 빨강 경보는 평가 블록에서 F1 0.931(95% 구간 0.892–0.955), 오경보 3 window다.**`
- PDF에서는 헤드 메시지를 본문과 구분되는 상자로 표시한다(`build_report_pdf.py`의 `p.head`).
- **헤드 메시지만 순서대로 모은 목록**(`check_style.py --heads`)을 읽어 보고서 전체 논리가 이어지는지 확인한다.

**확인 방법**: `check_style.py`가 절마다 헤드 메시지의 존재, 한 문장, 80자 이내, 숫자 포함을 검사한다.

### 규약 7. 도식화할 수 있으면 도식화한다

**원칙.** 줄글보다 표가 낫고, 표보다 차트가 낫다.

**이 보고서에서의 규칙**

- 숫자 3개 이상을 나열하는 문장은 표로 바꾼다.
- 각 장의 핵심 주장 1개는 차트로 보인다.

| 장 | 차트 |
|---|---|
| 1장 | 버스트 타임라인, 버스트 길이 분포 |
| 2장 | 오경보 감소 단계(241 → 35 → 3), 같은 구조 안 후보 비교(F1·FPR과 구간) |
| 3장 | 교란 대조(실제 고장 AUROC 대 가짜 고장 AUROC), 계측 섭동별 빨강 증가 |
| 4장 | 4상태 경보 흐름도 |

- 차트는 `report/make_report_figures.py`로 만든다. 원천 CSV는 출처 줄에 적는다.

### 규약 8. 색은 최대 3가지, 변화는 명도로

**원칙.** 한 페이지 안에서 색은 최대 3가지다. 더 필요하면 색을 바꾸지 않고 명도를 바꾼다.

**이 보고서의 팔레트** (색각 이상 검증 통과: 파랑–빨강 정상시 ΔE 32.3, 색각 이상 ΔE 21.6)

| 역할 | 색 | 쓰는 곳 |
|---|---|---|
| 주 계열 | 파랑 `#2a78d6` (옅은 단계 `#9ec5f4`) | 데이터 계열, 정상 |
| 강조 | 빨강 `#e34948` | 제출 시스템, 고장, 빨강 경보, 약점 |
| 맥락 | 회색 `#8a8985` | 비교 대상, 기준선, 축 |

- 범례 대신 **직접 라벨**을 우선한다. 색만으로 정보를 구분하지 않는다.
- 표에는 색을 쓰지 않는다. 강조는 굵게만 한다.

**확인 방법**: `check_style.py`가 보고서에 들어간 그림의 유채색 색상군 수(회색 제외)가 3 이하인지 검사한다.

## 3. 제출 전 검토 체크리스트 (수동)

- [ ] **규약 1**: PDF만 받은 검토자가 장별 주장을 설명하고, 그 설명이 헤드 메시지와 일치한다
- [ ] **규약 2**: 각 절의 주장이 1개다
- [ ] **규약 3**: 절마다 "헤드 요소 ↔ 근거 표·그림" 대응이 빠짐없다. 고아 표(어느 요소에도 연결되지 않는 표)가 0개다
- [ ] **규약 6**: 헤드 메시지 목록만 읽어도 문제 → 진단 → 모델 → 결과 → 실패 조건 → 활용 → 차별성 → 재현의 흐름이 이어진다
- [ ] **규약 7**: 숫자 3개 이상을 나열한 문장이 남아 있지 않다. 장별 핵심 차트가 있다
- [ ] **규약 8**: 그림 색이 팔레트 3색 안에 있다. 표에 색이 없다
